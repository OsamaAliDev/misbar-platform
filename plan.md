# Phase 5A — SaaS foundation

Continue the existing Misbar React/JavaScript app from latest main e1bad49 on saas-foundation only. Reuse its Cairo font, cream/night token system, plain CSS, rounded panels, accents and existing heroes. No redesign, analytics, parent accounts or payments. The existing site cannot be attached to this session; this phase is branch-only and is not a publication.

The forward SQL migration upgrades the legacy Supabase tables without erasing them, closes its anonymous event ingestion, adds school tenancy, and makes privileged writes explicit. Students use anonymous Supabase Auth identities bound to a class nickname only after server-side PIN verification. Staff use Supabase email Auth and trusted manually provisioned profiles. Platform admins manage aggregate counts through a constrained RPC and cannot query child rows. Subscriptions remain schema-only for a later phase; teachers are limited to their own classes. PostgreSQL tests execute real RLS locally using auth stubs; this is not a claim of remote Supabase verification.

No Supabase URL/key is available. A clearly labeled local mock HTTP backend uses salted server-side scrypt PIN hashes, opaque sessions, tenant/teacher ownership checks, rate limiting and the same browser API. It is separate from guest localStorage. Real Supabase configuration never silently falls back on errors. A small browser data-access module provides guest localStorage and server-backed adapters. On student login, local guest progress is imported once, validated and bound to the authenticated child; further actions use server-authoritative totals. Guests remain unchanged. Importing legacy client data is necessarily a bounded trust concession, recorded in DECISIONS.md.

## Structure

`supabase/migrations/` contains forward schema/RLS/RPC migration; `supabase/tests/` holds local SQL bootstrap and executable school-isolation proof. `server/` holds built-in Node HTTP serving, mock storage/security and Supabase REST/Auth transport. `src/lib/data-access.js` owns browser persistence/transport; `src/state/saas.jsx` owns session and school access; `src/state/student.jsx` retains the guest reducer and uses canonical server progress for signed-in students. `src/views/saas/` contains the two logins, classes, roster/enrollment. `src/i18n/locales/{ar,en}/saas.js` adds matching dictionaries. `docs/saas/` records actual evidence and screenshots.

The development listener stays on3000; Vite forwards `/api/saas` to the local backend on3002. The production Node server serves compiled dist and API together on PORT/default3000. Anonymous Supabase sign-ins and the SQL migration must be enabled/applied by the owner before real operation. No secret is bundled or committed. New staff accounts are created in Supabase Auth by the owner and assigned a school/role through trusted owner SQL.

Latest owner guidance (13:31) takes precedence: no subscription gate or manual subscription management in this run; seven foundation steps only. STATUS.md is pushed after each verified step/sub-step.
